# Аккаунты: вход через Telegram, всё в профиле

Решение владельца (02.11.2026): сайт открывается только после входа; вход — только через Telegram; делать сейчас, параллельно с v3.
Этот файл — передача между сессиями: статус этапов обновлять здесь.

## Зачем

Сейчас «личность» — браузер: `sr_settings`, `sr_journal`, `sr_bot`, `sr_ubot` (id + secret серверного бота) лежат в localStorage.
На другом устройстве всё создаётся заново: второй серверный бот, вторая привязка Telegram, другие настройки.
После: один профиль на человека, с любого устройства одно и то же; Telegram привязан к профилю сам, потому что вход через него.

## Как работает вход

1. Сайт: «Войти через Telegram». Вкладка создаёт случайный `secret` (32 байта), отправляет в функцию `auth` только его хэш,
   получает `nonce` и короткий код из двух эмодзи и открывает `https://t.me/<бот>?start=login_<nonce>`.
2. Бот (`supabase/functions/_shared/tg.ts`, ветка `/start`): «Вход на сайт Sigma Radar. Код на сайте: 🍋🚀?» — три кнопки с
   кодами (одна верная) и «Это не я». Вход подтверждается только верным кодом. Запрос живёт 5 минут, используется один раз.
   Защита от подмены: злоумышленник, приславший чужому человеку свою ссылку входа, без кода на экране этой вкладки не пройдёт.
3. Вкладка опрашивает `auth` (`nonce` + `secret`) раз в 2 с. После подтверждения функция service-ролью находит или создаёт
   пользователя Supabase Auth для `tg_id` (почта-заглушка `tg<id>@users.invalid`, письма никогда не отправляются),
   делает `admin.generateLink({type:'magiclink'})` и отдаёт `hashed_token`. Вкладка меняет его на сессию через REST
   `POST /auth/v1/verify` (`type: magiclink`, `token_hash`). supabase-js не подключаем: на сайте нет чужих скриптов (2.52),
   хватает своих ~40 строк — verify, refresh (`/auth/v1/token?grant_type=refresh_token`), logout.
4. Сессия — в `sr_auth` (access 1 ч + refresh). `rpc()` (index.html ~2273) отправляет access-токен вместо анонимного ключа;
   обновление за минуту до истечения и при возврате на вкладку; при 401 — одна попытка обновить, потом экран входа.

Функция `auth`: ограничение частоты по адресу (как у `ub_create`), `--no-verify-jwt`, добавить в `.github/workflows/deploy-functions.yml`.

## Данные

- `profiles`: `id` = `auth.users.id`, `tg_id` (unique), `tg_name`, `tg_username`, `is_owner`, `beta`, `created_at`.
- `user_state`: (`user_id`, `key`) → `value jsonb`, `version int`, `updated_at`. Ключи: settings, favs, bot (BP), journal, tfilt и т. п.
  Запись с проверкой версии: чужая более новая версия → взять её и наложить своё изменение заново (два устройства не
  затирают друг друга). Журнал — с потолком размера (старые закрытые сделки обрезаются, как сейчас в браузере).
- `user_bots.user_id` (unique): один серверный бот на профиль. `ub_*` получают вариант по `auth.uid()` без secret;
  старые по secret остаются до конца переноса.
- Telegram: чат личных сообщений = `tg_id`, поэтому «Подключить Telegram» превращается в переключатели. `ub_tg_link` по коду — убрать после переноса.
- «Бета»: отметка `profiles.beta`; коды SR-… (`beta_redeem`) включают её на аккаунте. Владелец — `is_owner`
  (ставит владелец сам в SQL Editor); пароль владельца беты после этого не нужен.
- RLS: владелец строки — `auth.uid()`; анонимный ключ личных данных не читает и не пишет.

## Первый вход на устройстве с данными

Есть локальные `sr_*` и/или `sr_ubot` → диалог: «Перенести данные этого устройства в профиль?».
- Профиль пустой → перенести (серверный бот привязывается через `ub_claim(id, secret)`).
- В профиле уже есть данные → по умолчанию «Взять из профиля», вторая кнопка «Заменить данными этого устройства».
- Два серверных бота (профиль и устройство) → спросить, какой оставить; второй удалить через `ub_delete`.
