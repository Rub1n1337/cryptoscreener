# Грабли и как их обошли

Что ломалось при разработке Sigma Radar, почему и как это исправили. Подробности в сообщениях коммитов (хэш в скобках).

## Коротко перед работой

Ошибки, которые уже повторялись. Читать каждую сессию; таблицы ниже — искать grep'ом по разделу, который трогаешь.

1. Кириллицу и другие не-ASCII символы менять только через Edit. `perl`/`sed`-замены портили весь файл (двойная кодировка) и теряли `\u`.
2. Функции `bot` и `tg` выкладывает GitHub Actions при пуше в `supabase/functions`.
   - Нужную им миграцию применить **до** пуша.
   - После пуша проверить, что запуск успешен, что номер версии вырос и что в `bot_runs` нет ошибок. Код выкладывается прямо из репозитория, поэтому сверять файлы не нужно.
   - `get_edge_function` для `tg` возвращает ~30 КБ прямо в разговор: без нужды не вызывать.
   - Ручная выкладка через MCP — только запасной путь: все три файла, JSON с экранированными `\uXXXX`.
3. Миграция:
   - сначала прогнать её с проверками в транзакции, которая заканчивается `raise exception` (откат);
   - при смене подписи функции старую удалять в той же миграции, новым параметрам давать значения по умолчанию, права выдавать заново.
4. Порядок выкладки: миграция (обратно совместимая) → функция `bot` → сайт.
5. Правка `math.js`:
   - сохранить прежнюю копию в `tests/_ref/math.js`;
   - пройти `tests/math.html?ref=_ref/math.js`: сделки и отпечаток анализа должны совпасть.
6. После пуша проверить, что Vercel отдаёт новую версию; если нет — выложить вручную с `withLatestCommit`.
7. Превью:
   - скрытая панель останавливает `requestAnimationFrame`;
   - `focus()` и `scrollIntoView` сдвигают координаты для мыши;
   - текст в `::after` не виден в `scrollWidth` — ширину мерить через `canvas.measureText`;
   - затемнённый скриншот — помеха захвата, переснять.
8. Таблицы и формы на телефоне проверять на 320 px: там обрезается то, что влезает на 375.
9. Состояние, которое меняют двое (шаг бота и действие пользователя), защищать блокировкой строки и номером версии, а не надеждой на редкость совпадений.
10. Тексты вида «$10 000», «10 000» и числа из исследований не зашивать: брать из данных или показывать, только пока данные совпадают с проверенными.

## Сервер: Edge Function `bot`, коллектор на Railway

| Проблема | Причина | Решение |
|---|---|---|
| С 19.10 не создавался серверный бот («column reference k is ambiguous») и не принимались коды беты | в `_rl` параметр `k` и столбец `k` таблицы `rl`: `on conflict (k)` неоднозначен, функция падала при каждом вызове; проверяли только SQL-текст, ни разу не вызвали; а вход в бету показывал любую ошибку сервера как «нет связи», и искали VPN | ключ через `$1`, конфликт по `rl_pkey` (2.40). Новую SQL-функцию вызывать сразу после выкладки в транзакции с откатом; ошибку сервера показывать её текстом, а не «нет связи» |
| Прогон бота шёл ~40 с, личные боты не успевали | ~600 мелких запросов к Binance, по 10 одновременно | 25 запросов одновременно: 40 → 17 с (94d1a80) |
| Бот падал из‑за нехватки памяти и CPU | свечи хранились строками Binance (12 строк на бар), анализ одной монеты считался заново для каждого бота | компактные числа, один анализ на монету и настройки канала для всех ботов (2636981) |
| Кэш свечей в памяти функции не давал экономии | Supabase **запускает функцию заново на каждый вызов** (boot → прогон → shutdown), кэш живёт один прогон | свечи держит коллектор на Railway (`POST /scan`), бот берёт всё одним запросом (10002d2, 626f457) |
| Коллектор не подогревал свечи, на которых торгуют | запрос сигналов перезаписывал `s.lazy` поверх торговых | отдельная метка `tradeAt` (13ba6c6) |
| Бот мог взять анализ, посчитанный по другим правилам | коллектор грузит math.js с сайта, сайт и функция обновляются не одновременно | `M.fingerprint()`: анализам коллектора бот верит только при совпадении отпечатка, остальное считает сам (626f457) |
| Минута терялась целиком из‑за 418 от Binance | общий исходящий адрес Supabase, один отказ на тикер за 24 ч | тикер хранится и переиспользуется до 15 мин; оповещение только после 3 отказов подряд (4dd9065) |
| Торговля пропускала минуты, когда сканы уведомлений съедали бюджет | сигналы считались до торговли | сначала торговля всех ботов, сигналы делят остаток (v29) |
| При деплое коллектор терял стакан | `npm start` не передавал SIGTERM в node | запуск `node` напрямую (eb1ad86) |
| Бесконечные пересинхронизации стакана и бан Binance | события, пришедшие во время загрузки снимка, выбрасывались | одна синхронизация на график, снимки с интервалом 1.2 с (c7e0864) |
| Фьючерсный стакан пустел у цены | снимок на 1000 уровней покрывает только ±0.15 %, обновления за его пределами отбрасывались | изменения за пределами снимка сохраняются (6e5d398) |
| `POST /scan` мог вызвать кто угодно: тысячи загрузок с Binance за запрос, бан IP коллектора | маршрут был открыт, а отпечаток math.js коллектор сам отдавал в ответе на ошибку | токен `SCAN_TOKEN` = `bot_secret.scan`, отпечаток не отдаётся, не больше 900 полных загрузок в минуту (аудит 19.10) |
| Мусорные «Мои боты» могли занять очередь, стопы настоящих ботов запаздывали | `ub_create` без входа, лимит 30 в час общий, бот сразу включён | лимит 5 в час на адрес, бот создаётся выключенным, в очередь только боты с профилями, боты с позициями первыми (аудит 19.10) |
| Баланс бота мог разойтись со сделками, ручное закрытие могло потеряться | сделки, позиции и баланс писались отдельными запросами, ошибка баланса не проверялась; запись позиции затирала `closeReq` | одна транзакция `bot_commit` / `ub_commit`, `closeReq` сохраняется (аудит 19.10) |
| Хэш пароля владельца беты лежал в коде сайта | проверка пароля в браузере | проверяет только сервер (`beta_owner`), bcrypt, попытки считаются по адресу (аудит 19.10) |
| «Переключатель» торговал отскоки, когда не загрузились свечи BTC | `modeOf` считал неизвестный режим боковиком | неизвестный режим — не входить; в бэктесте режим известен всегда, итоги те же (2.37) |
| Отказ коллектора был не виден | прогон всё равно `ok`, ошибка оставалась только в ответе функции | пишется в `bot_runs.error` успешного прогона, в «Работе сервера» — жёлтая клетка (2.37) |
| Отпечаток math.js не замечал изменений силы сигнала, разворота и пробоя | на его синтетических свечах цена ни разу не доходила до границ канала: касаний, силы и пробоев в хэше не было | свечи с резкими движениями, затишьем и объёмами чуть выше и чуть ниже порогов, плюс каждая свеча как в бэктесте; проверено: любой порог в любую сторону меняет отпечаток, правка комментария — нет (2.35) |
| Боты с позициями сверх 40 могли не запускаться вовсе | «боты с позициями первыми» брались в порядке таблицы: каждую минуту одни и те же 40 | они тоже по давности проверки, и 10 мест всегда остаются ботам без позиций (2.35) |
| Сброс серверного журнала мог «откатиться»: позиции и баланс из прошлого журнала возвращались | шаг бота читал позиции до сброса и записывал их обратно в `ub_commit` после него | `user_bots.reset_n`: `ub_reset` увеличивает его, `ub_commit(…, p_gen)` отказывается писать, если номер сменился, и бот не объявляет сделки отказанного шага; обе функции сначала блокируют строку бота (2.46) |
| `/heat` коллектора отдавал ~4 МБ JSON для BTC на каждый открытый график и собирал его заново каждый раз | сутки по минутам, ±12 % от цены, значения в долларах; кэша не было | `?tf=` сворачивает минуты в свечи таймфрейма (максимум по клетке, как в браузере), значения в единицах `u` (~1/100 медианы), готовый gzip в кэше на монету, таймфрейм и начало, пока не закроется новая минута. BTC: 5м 4.1 МБ → 0.48 МБ, 15м — 0.16, 1ч — 0.04; ошибка ≤ 0.15 % на заметных клетках. Запрос без `tf` (старая вкладка) получает прежний формат байт в байт (2.55) |
| Смена подписи функции в базе ломает вызовы | функция с новым параметром создаётся рядом со старой, и вызов с прежними аргументами становится неоднозначным; у `ub_commit` менялся и тип результата | старую подпись удалять в той же миграции, новым параметрам давать значения по умолчанию, права выдавать заново; сначала прогнать миграцию с проверками в транзакции, которая заканчивается исключением (откат) |
| Railway съел включённые в Hobby $5 к середине цикла и ушёл в перерасход ($8 за 16 дней) | считали только трафик, а Railway берёт поминутно за память и процессор; стаканы шли каждые 100 мс (в 6 раз больше сообщений, чем нужно тепловой карте раз в 10 с), стакан хранился до ±25 %; измерений не было | `/health` → `res`: процессор, память (и cgroup, как считает Railway), разбивка процессора и исходящего трафика по частям, сетевая карта (`net`). Стаканы раз в 1 с (спот) и 500 мс (фьючерсы), стакан до ±15 %, `--max-semi-space-size=4`. Исходящий трафик — это прежде всего **TCP-подтверждения входящих потоков**: по пакету на каждый пакет от Binance (~180 в секунду, ~75 % исходящего, ~$1.6 в месяц), ответы `/scan` — лишь ~250 КБ в минуту. Значит, цена потока растёт с числом сообщений, а не с байтами. Итог 29.10: ~0.11 vCPU, ~334 МБ, ~1 МБ в минуту исходящего ≈ $7.7 в месяц (до правок — ~$15). Перед новой нагрузкой на коллектор (монеты, история, поток) прикидывать цену |

## Уведомления в Telegram

| Проблема | Причина | Решение |
|---|---|---|
| Первый настоящий сигнал «проглатывался» | пустое состояние считалось первым запуском | пустое состояние ≠ первый запуск (f3a13f9) |
| Сигнал приходил на касание, а подтверждение разворота не приходило никогда | касание запоминалось один раз | одно сообщение на касание, оно редактируется при подтверждении и при входе бота (5756d20) |
| Одна монета приходила 2–3 сообщениями (общие правила, профиль, «Рынок») | независимые потоки | поток «≥ 60» убран, «Рынок» пропускает монеты, о которых уже сказали «Мои сигналы» (5756d20) |
| В Telegram менялись сигналы, когда на сайте просто переключали таймфрейм | «Рынок» брал настройки с открытой страницы | настройки сохраняются явно кнопкой (5756d20) |
| Одно и то же касание повторялось на каждой новой свече (WAL) | ключ = время касания, а цена стоит за границей несколько баров | эпизод: одна монета и сторона в пределах `TOUCH_BARS` свечей = одно сообщение (d552192) |
| Тихие часы «прилипали» к следующему прогону | множество `QUIET` в тёплом экземпляре не очищалось | очищается в начале каждого прогона (d552192) |
| Сигнал терялся, если Telegram не принял сообщение | эпизод записывался как отправленный сразу, с `mid` 0 | неотправленное помечается `retry` и уходит снова, до трёх прогонов; списки «Ещё сигналы» и «Рынок» — так же (2.37) |
| Одно касание могло прислать ложное «отскок не удержался» | эпизод жил под несколькими ключами одного объекта; в JSON базы они становятся копиями и расходятся | один ключ на эпизод, старые копии удаляются, остаётся самая свежая (2.37) |
| В `money()` ломался формат сумм после деплоя | регулярка содержит буквальный неразрывный пробел, он терялся при копировании | в JSON деплоя писать ` `, после деплоя сравнивать с репозиторием (94d1a80) |
| Сообщение сигнала могло навсегда остаться «ждём подтверждения» | правка (`tgEdit`) не проверяла ответ Telegram, а стадия эпизода менялась в любом случае | `tgEdit` возвращает, прошла ли правка; стадия меняется, только если прошла правка или короткий ответ, иначе до трёх попыток (2.39) |
| Telegram «Рынок» присылал около трети подтверждённых сигналов (на топ-100 1h за двое суток 1 из 3), друг решил, что сигналы идут только при открытом сайте | `marketSignals` проверял разворот по закрытой свече (`tradeRow`), а порог силы — по силе текущей свечи, у которой своё подтверждение ещё не выполнено (−20 баллов) | сила и разворот берутся с закрытой свечи, как в `mySignals` (2.41). Проверено пересчётом его настроек за те двое суток |

## Окружение разработки

- Локально нет Node, Deno и Python. Синтаксис JS проверяется импортом модуля в превью браузера: ошибка вроде «process is not defined» значит, что файл разобрался.
- Деплой функции: MCP `deploy_edge_function` с полными `index.ts`, `../_shared/math.js`, `../_shared/tg.ts`, `verify_jwt: false`. После деплоя `get_edge_function` и diff с репозиторием.
- Правки больших блоков в index.html делать через Edit или точную замену, которая падает, если блок найден не ровно один раз. `perl -0pi` однажды вставил текст в начало файла.
- В заменах `perl -pi` не писать не-ASCII символы (`\x{2013}`, кириллицу): perl читает файл байтами, и вставка «широкого» символа перекодировала весь index.html — кириллица стала двойным UTF-8 (21.10, ~1000 мест, восстановлено обратным преобразованием). Такие правки — через Edit; после любой правки скриптом проверять `grep -c "Ð" index.html` и валидность UTF-8.
- В Bash нельзя `sleep` и `rm` после `cd`: ждать через фоновые задачи, временные файлы класть в новую папку.
- Пуш в `main` сразу выкатывает сайт на Vercel, а `server/` выкатывает коллектор на Railway.
- Railway может не подхватить пуш (28.10, 2.55: выкладки нового коммита в списке не было вовсе), а на GitHub он следов не оставляет — ни статуса, ни выкладки. После пуша в `server/` проверять `uptime` в `/health` (обычно сбрасывается через ~4 минуты) и новый маршрут или поле; если нет — владелец в панели Railway: Settings → Source (репозиторий, ветка `main`, Root Directory `server`), затем Ctrl+K → Deploy Latest Commit (Redeploy старой выкладки соберёт старый код). Клиент «Беты» должен работать и со старым коллектором. Через ~2 минуты после ручной выкладки коллектор перезапустился ещё раз (~45 с Railway отвечал 404 «Application not found»), причина не выяснена — вероятно, вторая выкладка; запросы по одному его не роняли, дальше стоял. Такой 404 сразу после выкладки проверять наблюдением `uptime` без нагрузки, а потом запросами по одному.
- Vercel иногда пропускает пуш (21.10: коммит в `main` есть, выкладки нет). После пуша проверять, что сайт отдаёт новую версию (`curl … | grep "v:'2.NN'"`); если нет — повторная выкладка через Vercel MCP `create_deployment` с `deploymentId` последней и `withLatestCommit: true`.
- Порт 8765 может быть занят сервером другой сессии (`HttpListener`, в `netstat` — PID 4), который отдаёт другую копию репозитория. Проверка: `curl -s localhost:8765/index.html | grep -c <своя правка>`. Тогда свой сервер — копия `serve.ps1` в папке для временных файлов с путём к своему worktree и портом 8766, плюс запись в `.claude/launch.json` (он не в git) (2.56).
- Масштаб и прокрутку графика удобно проверять на стенде: свой canvas через `window.__sr.kit` (`renderChart`, `attachZoom`, `viewRange`) с синтетическими свечами — вид виден числами после каждого синтетического `WheelEvent` / `TouchEvent` (`new Touch(...)` работает в превью) (2.56).
- Проверка в превью: когда панель браузера скрыта, `requestAnimationFrame` не срабатывает. Скрипт, который ждёт кадр, «зависает» по таймауту и доделывает действия позже, когда панель покажут. В тестах ждать через `setTimeout`, а то, что выполняется в кадре (`alignNums`, `rove`, `perFrame`), проверять при видимой панели (например, после скриншота).
- Долгие расчёты в превью (исследования):
  - при скрытой панели таймеры в фоне замедляются, поэтому темп запросов к Binance задаётся числом одновременных запросов (6), а не паузами;
  - `javascript_tool` ждёт не дольше 45 с: опрашивать с паузой ≤ 44 с; долгий синхронный цикл расчёта может сорвать один опрос;
  - стенд хранить в `research/` в репозитории — стенд 19.10 жил только в превью и потерялся;
  - `data-api.binance.vision` отдаёт старые часовые свечи с задержкой ~2.3 с до первого байта: 6 потоков — это ~4 запроса в секунду и ~50 минут на три года. Ограничивает задержка, а не трафик, поэтому `fib.js` берёт 16 потоков (`par`) — ~800 веса в минуту при лимите 6000, прогон ~9 минут. 4h собирать из 1h, а не грузить второй раз.
- Обрыв WebSocket в превью (разбор «Беты» 28.10): соединение на закрытый или чужой адрес (`wss://127.0.0.1:9`, `:59999`) превью переводит в CLOSED без события `close`, и код переподключения не срабатывает — это помеха превью, не баг сайта. Обрыв имитировать так: подменить `window.WebSocket` наследником, который закрывает сокет на `open`; «тихий» поток — наследником, который не передаёт `onmessage` (сеттер `onmessage` в классе-наследнике оборачивает обработчик, режим можно менять на живых соединениях). Ловить замеры — обёртками `requestAnimationFrame`, `setInterval`, `fetch` и `__sr.kit.renderChart` (данные свечей графика).
- Замеры кадров в превью (2.55): панель может быть «показана», а `document.visibilityState` — `hidden` (окно приложения в фоне); тогда кадров ~1 в секунду и миллисекунды кадра ничего не говорят. Проверять `visibilityState` во время замера; если документ скрыт, сравнивать старый и новый код в одних условиях по числу графиков за кадр (старый `beta.js` из `git show HEAD:beta.js` на место нового, свой — копией в `tests/_ref/`, потом вернуть и сверить `cmp`).
- Замер 4 графиков «Беты» (2.57): `WebSocket` подменять до открытия «Беты» — страница перезагружается на `#market` (`history.replaceState` + `location.reload()`), подмена, потом `location.hash = '#beta'`; переход по hash без перезагрузки оставляет старые соединения и прежнюю раскладку в памяти модуля. Скрипт дольше ~40 с превью обрывает: запуск счётчиков и сбор итога — двумя вызовами. Обёртка `requestAnimationFrame` видит все циклы страницы, поэтому «графиков за кадр» считать по вызовам `__sr.kit.renderChart` внутри одного обратного вызова.
- CSP сайта запрещает `eval` и `new Function`, и в превью тоже. Код коллектора (`server/index.js` импортирует `ws` и `node:*`) проверять так: нужный участок вырезать скриптом в модуль в `tests/_ref/` (папка в `.gitignore`), добавить `export` и заглушки и импортировать его в превью; на нём прогнать настоящий ответ коллектора.
- Правка `supabase/functions/_shared/math.js`: перед ней сохранить прежнюю копию (`git show HEAD:supabase/functions/_shared/math.js > tests/_ref/math.js`, папка в `.gitignore`), после — открыть в превью `tests/math.html?ref=_ref/math.js`. Страница сравнивает сделки и отпечаток анализа с прежней версией и проверяет размер позиции и просадку. Все проверки должны пройти. Коллектор на Railway берёт `math.js` с сайта и отвечает боту, только пока отпечатки совпадают.
- Выкладка функции `bot` через MCP: файлы передавать JSON-строками, в которых всё, кроме ASCII и кириллицы, экранировано `\uXXXX`. Неразрывный пробел в `tg.ts` и вариационные селекторы эмодзи (U+FE0F) невидимы и при переписывании теряются. В perl обратную косую черту для `\u` собирать через `chr(92)`: в замене `s///e` строка `"\u…"` теряет `\u`. Перед выкладкой проверить, что декодированный JSON совпадает с файлом, после — сравнить `get_edge_function` с репозиторием байт в байт.
